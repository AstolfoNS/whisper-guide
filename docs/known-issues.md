# 已知问题与现场验收边界

更新日期：2026-10-24。本记录依据 `fc2ac03` 代码及后续只读排查整理；本次仅更新文档，未修改或修复以下业务路径。已有自动化回归结果见[验收记录](acceptance-round-1.md)和[存储瘦身记录](storage-slim-2026-10-24.md)。

## 噪声被过滤后自动提示仍暂缓

**状态：已复现，未修复。** 部分声音被 VAD 判为人声后，后续识别即使标为“已过滤”，静音等待到期也可能持续停留在“识别”，不自动播报。

当前实现路径：

1. 讲稿曾成功对齐，当前位置可靠。
2. VAD 触发 `speech_start`，领域层保存先前可靠标记，并将 `reliable` 置为 `false`，等待此次语音确认位置。
3. 识别结果缺少相应分段人声证据，运行时标记“已过滤”并返回，没有将其送入定位器；该分支也没有结算此前的待确认可靠标记。
4. 后续 `speech_end` 可以开始静音计时，但 `tick` 要求 `reliable=true` 才允许自动提示，因此计时到期仍不播报。

代码依据为[领域会话](../backend-core/app/domain/session.py)的 `speech_start`、`speech_end`、`tick`，以及[识别运行时](../backend-core/app/api/session.py)的声学证据过滤分支。该路径已通过内存合成输入复现；它能够解释用户截图，但不能据此断言每次现场不播报都由同一原因造成。

临时处理：先确认自己已读到的实际讲稿位置，再使用工作台“手动定位”设定可靠起点；或继续清晰朗读当前位置附近的讲稿，等待有效结果成功对齐。需要立即获得提示时可使用“手动提示”，但该操作不能证明位置已恢复可靠，也不会根治此路径。不要为了恢复播报而删除模型方案、替换 API Key 或取消真实脱稿的低置信度保护。

后续修复需要区分“噪声已过滤”“等待有效结果”“真实讲稿失配”，并覆盖真实开口、轻声、回读与脱稿场景；不能将所有过滤结果一律视为可靠，以免从错误位置继续播报。

## 讲稿匹配百分比与警告可能误导

**状态：界面误归类已确认，未修复。** 当前“讲稿匹配”的百分比来自最近一次已保存的 `match_confidence`。新声音使位置进入待确认时，它可能仍显示上次的 `100%`，并非当前噪声转写或整段语音识别的准确率。

前端[TranscriptComparison.vue](../frontend/src/components/studio/TranscriptComparison.vue)主要根据 `reliable`、是否说话及原始文本/final 组合生成提示。在“被过滤的 final + 位置仍待确认”路径中，也可能显示“未能可靠匹配讲稿，自动播报已暂停”，此时并没有把该条过滤结果送入对齐器验证失配。提示中的“暂停”表示自动播报暂缓，五状态机仍可能处于 `LISTENING`，不能将它等同于进入 `PAUSED`。

阅读界面时分别查看：

- “实时识别 / 已过滤”：模型返回过这段文字，但该条文字未用于讲稿定位；不代表录音被保存。
- “讲稿匹配”：最近成功对齐的原文及评分，可能保留上一条结果。
- “五状态机”：当前真正的会话状态及最近迁移原因。

计划改进方向为明确标识“上次匹配”，并将待确认、过滤与真实失配分别呈现。本次文档更新不包含该 UI 改动。

## 抗噪与云端验收限制

浏览器请求的降噪、WebRTC VAD、能量门控及分段声学证据均有边界。较强背景噪声、回声、外放提示音和旁人的讲话仍可能被判为人声并进入识别。云端或本地 ASR 返回文字，也不证明对应的声音来自当前演讲者。现有链路不提供说话人身份隔离，不能保证所有杂音均被剔除。

建议在目标设备上用耳机、稳定的麦克风距离和相对安静环境做对照，再分别验证正常朗读、轻声、填充词、停顿、回读、外放回声与背景声音。必要时记录发生时的状态、识别来源和过滤标记；不要把用户录音或密钥写入日志或公开问题报告。

`/api/health` 的 `ok` 及 STT/VAD/TTS 的 `ready` 表示对应健康或依赖能力检查通过，不等价于真实云端识别准确率、TTS 合成成功或浏览器扬声器能播放。付费云端的鉴权/短静音探测、真实中文识别、目标设备长时抗噪应分别验收。历史通过的模拟测试与数字静音测试不覆盖上述所有现场条件。

排查步骤见[运维手册](operations.md)；新服务器的网络、远程麦克风访问和部署步骤见[部署手册](../DEPLOY.md)。
